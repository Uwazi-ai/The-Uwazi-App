# Backend rules
- Rider email is optional and stored only on ride_requests.email; one-off rights recipients are never saved, email never enters zTrip, Autocab, calls text, exports or logs, and is included with rider contact data in the purge plan. Service-only event claims and keyed address hashes enforce delivery limits; coordinator-email-reminder validates coordinator access and today/tomorrow Central requested/booked eligibility before sending one fixed reminder. SMS reminders and schedules stay unchanged. Why: private ride communication must not expose contact data or block saved rides and quizzes.
- Compass event demos persist only anonymous persona/top-issue/duration totals in compass_demo_results via log_demo_completion; active windows and persona validity are checked server-side, and a one-run result UUID deduplicates retries without identifying a participant. evaluate_compass_demo calls existing persona_label with no writes. Event controls and result reads require super_admin. Why: minors can explore without accounts, identity collection, entitlements or engagement writes.

- Office data changes flow only through civic_office_pending_changes + review_office_change RPC; office-monitor never writes civic_offices. Why: every officeholder change needs explicit admin approval.
- Civic Journey points are written only by SECURITY DEFINER functions (award_points via complete_compass_session, award_lesson_completion, award_report_unlock, log_civic_action, survey trigger); user_points_ledger is append-only by trigger. Why: points must never be trusted from the client.
- Journey reads go through get_my_journey and get_my_path RPCs, which hide identity and scores unless consent_scope.personalization is true. Why: consent is enforced server-side in one place.
- Ask UWAZI journey context is built per turn in supabase/functions/ask-uwazi/journey.ts and sent with the user message, not in the system prompt. Why: keeps the cached system prompt static.
- Candidate lists refresh through office-monitor sources with kind=candidates; changes land in civic_office_pending_changes and only review_office_change writes race_candidates or ballot_candidates. Why: candidate changes need the same explicit approval as offices.
- District codes are resolved server-side in resolve-address and stored in user_districts (codes only, never the address or lat/lon); district_boundaries rows start active=false and must be activated per import batch before any point-in-polygon match uses them. Why: address data stays out of the app and unverified boundaries never drive who represents me.
- New cities are found by the city-discovery function from city_onboarding rows that resolve-address requests; it only creates sources and boundary batches with active=false, and a city flips to active by trigger once one source and one boundary batch for its place_geoid are on. Why: nothing a search finds reaches voters without admin approval.
- Compass 2.0: identity photos live in a private bucket keyed by user id; city identity summary only via city_top_identity (25+ research-consented, never rows). Why: photos and answers stay private.
- Civic Games counts are rebuilt only by refresh_challenge_progress from user_points_ledger (distinct source_id per event), and challenge_progress is never written by the client; ZIP boards come from challenge_zip_board, which hides ZIPs under 10 participants and never returns a user. Why: standings must be earned server side and no one is ever shown by name.
- Consent changes, identity fit picks, data export, and Compass data deletion go only through set_my_consent, choose_identity_dimension, export_my_data, and delete_my_compass_data RPCs; self reported civic actions are written with verified=false. Why: privacy controls act on the caller only and stay server side.
- Scheduled system jobs (nightly-backup, health-check) authenticate with the private token in system_job_token, read by pg_cron at call time, or a super_admin sign-in. Why: no job secret is written into cron SQL or the repo.
- Civic personas are assigned only in persona_label/complete_compass_session/choose_identity_dimension and read from compass_personas; persona_history is written only by those functions. Why: persona logic stays server side and copy is editable without code.
- Public persona reads require is_public; public poster reads require an exact published episode filename, and active clip access excludes paid/unpublished episode originals and playback variants. Why: new catalog rows and protected media cannot accidentally become public through broad read rules.
- Research surveys live in survey_definitions, survey_dispatch and research_survey_responses, separate from the older outreach surveys tables; sending goes through send_research_survey or the hourly dispatch_due_surveys job, answers only through submit_research_survey, and admins read only research_survey_results totals. Why: only research-consented matching people get surveys and no answer is ever tied to a name on screen.
- UWAZI+ is sold only as the $19.99 monthly and $7.99 student monthly prices, with no free trial; checkout never sets trial days. Why: the price shown must be the price charged.
- Every UWAZI+ decision (episodes, list_published_episodes, Ask limit, My City, Compass report, Plus only lessons via can_open_lesson, report RPCs, journey) uses has_plus_access(user_id) (client: my_plus_access); it is true only for admin or an unexpired subscriptions row (paid, comp_, promo_, code_; student prices also need a verified student). is_plus is a thin wrapper; profiles.plan is display only and never grants access; never add a second rule. Why: comps and promos must work and expired grants must lose access.
- Each stored episode original keeps phone-safe copies beside it as <base>.h264.mp4 and <base>.webm, which resolve-episode-video lists first; every new upload must get the same two copies. Why: many phones and browsers cannot play the originals.
- Student pricing requires a verified student_verification row; student IDs are stored only as a salted one way hash. Why: no raw student numbers ever live in the app.
- My Ballot shows only ballot_contests with verification_status verified, matched to user_districts codes via matchContest in src/lib/districts.ts; researched contests are inserted unverified. Why: voters never see unchecked ballot data.
- The voter guide reads dates and places only from voter_guide_dates and voter_guide_sites rows with verification_status verified; county rows override statewide rows of the same kind. Why: the app never writes its own election dates.
- Rides to the Polls: the public writes ride_requests only through create-ride-request; coordinators (ride_coordinator role or admin via is_ride_coordinator) read and update status, a trigger logs every status change to ride_events, which is append-only, and destinations are only verified voter_guide_sites rows. Why: rider contact data stays server side and no vote choice is ever stored.
- Rides public reads go only through get-ride-availability (no personal data) and get-ride-card (code, time, status, destination only); Election Day destinations come only from the KCEB precinct map (or a coordinator), never Census voting districts. Why: riders are never exposed and polling places are never guessed.
- Jackson County early voting rides use ride_site_hours and ride_site_geo (service role only) through _shared/ride-sites.ts; get-ride-availability and create-ride-request share the same open at pickup plus 1 hour rule. Why: the form and the server must never disagree on what is bookable.
- Ride desk (/rides/desk) changes rides only through coordinator RLS updates so log_ride_status_change records status; other desk actions insert ride_events with actor = auth.uid(); phone rides enter only through create-phone-ride, which checks is_ride_coordinator and skips only the 24 hour rule. Why: every coordinator action is traceable and phone rides follow the same seat and site rules.
- Voter facing ride functions (get-ride-card, rider-update-stage, rider-finish-quiz, rider-rate-ride, rider-text-rights-card) need ride_code plus ride_requests.card_token via _shared/ride-token.ts and answer "Ride not found" for any mismatch; riders may move trip_stage 2 to 3, round trips 4 to 5, or complete a one-way trip from riding at stage 4 to completed at stage 7. Ratings are integers 1 to 5 on completed rides only; the quiz saves only quiz_score and quiz_finished_at. Why: ride codes are guessable and neither answers nor rating comments belong in storage.
- Rider rights-card and driver-on-way texts use atomic ride_requests delivery claims before the shared consent/opt-out checked sender. Ambiguous failures retain claims; only texted events establish sent delivery. The public demo is fixture-only and never invokes ride functions or reads ride tables; the legacy my_ride_demo_access remains read-only. Why: repeated taps cannot duplicate texts and marketing fixtures never write to rides.
- Rights quiz copy lives in rights_questions and is public only once approved_at is set by an approver. Why: legal copy must be reviewed before riders see it.
- Ride texts go only through _shared/ride-sms.ts (Bird), which checks texts_ok and ride_sms_optouts (SHA-256 of E.164 phone), logs texted or texted_failed to ride_events without the phone, and never throws; desk texts go through send-ride-text, which builds the message server side; reminders use send-ride-reminders with reminder_sent_at claimed before send. Why: riders only get texts they agreed to and a texting failure never blocks a ride.
- Know Your Voting Rights reads election_rules (timestamps, county rows override statewide by rule_key) and rights_cards, both public read and super_admin write; voter_guide_dates stays the date-only voter guide source. Checklist rows in voter_checklist_progress never award points. Why: rights copy needs exact times and the checklist must not become a points source.
- Bird inbound replies hit bird-inbound, which verifies the messagebird-signature HMAC with BIRD_WEBHOOK_SECRET and only upserts or deletes ride_sms_optouts hashes; the desk sees paused riders through ride_paused_ids. Why: opt-outs must be honored without exposing phones.
- Rights question approval and ride coordinator grants go only through admin-only RPCs (set_rights_question_approval, set_ride_coordinator), each logged to ride_admin_log with the acting admin. Why: legal approval and desk access must be traceable and never set by coordinators.
- Episode lists for Home and Watch come from list_published_episodes, which returns every published episode but a video path only when the caller may play it; episode posters live at home-video-media/episode-posters/{episode_id}.jpg. Why: free members see locked episodes instead of a blank feed, and no paid file path leaks.
- Ask UWAZI decides what skips the free count in ask-uwazi/free-prompts.ts: only a card id the server signed (issue_cards) or a reply in the session where the server stored a pending calibration question; the client source label is ignored, and check-ask-limit lets server-marked free messages through after the limit. Why: the count can't be skipped from the browser.
- Rides are only for the KCEB area: Census geocode must return county 29095 and place 2938000 (Kansas City city), checked by _shared/ride-eligibility.ts in create-ride-request, create-phone-ride, join-ride-waitlist and get-ride-availability; a failed lookup refuses online and only a coordinator may book by phone. Early ride destinations are only verified Jackson County early sites; poll_ride_waitlist is written only by join-ride-waitlist. Why: rides serve Kansas City Election Board voters only and the address is never guessed.
- KCEB precincts come only from the Kansas City Election Board ArcGIS layer (KCEB_Precincts_view FeatureServer/10) loaded into kceb_precincts (service role only) by load_kceb_precincts via the admin-only kceb-precinct-refresh function, which logs each reload to ride_admin_log; precinct_for_point (ST_Contains) is the only point to precinct match, used by ride-eligibility, ride intake and find-my-precinct, and no match means needs_destination or manual entry. Why: polling places are never guessed and map changes before Election Day can be reloaded.
- Ride booking uses only ride_service_days (locked dates, wave_times, cost_cents); driver_blocks no longer drive booking. Pickups are only the listed wave times, each wave seats ride_settings.seats_per_slot (3), and an early voting wave goes to the one site set by its first booking while Election Day waves may stop at several polling places; the enforce_ride_wave trigger guards both. KCEB area, 24 hour advance, site open at pickup plus 1 hour and Nov 2 Blue Parkway only still apply. Why: drivers are paid per scheduled block, not per hour.
- Ride budget is ride_settings.budget_cents against the sum of ride_service_days.cost_cents; funded_cap is retired. Only ride_requests.provider 'ztrip' counts toward budget, seats and cost per ride; iris, uber_voucher and other never do. Day list sign-ups (no_driver or full) save to poll_ride_waitlist with requested_date and reason after the KCEB check and never create a ride. Why: the $1,000 grant pays only for zTrip.

- ride_settings.sms_live defaults false and only admins can edit it; all ride SMS helpers and reminder claims skip without new delivery events when off, and bookings save texts_ok=false. Why: Bird is paused and no rider should be promised a text.
- zTrip heads-up texts are coordinator-sent sms: links to ride_settings.ztrip_text_phone (admin edit only), never server SMS. "Mark texted" logs ztrip_texted per ride with a status|day|time|destination note; a mismatch later shows "Update zTrip". Messages never include card_token or ride links, and single-ride messages name one rider only. Why: zTrip watches trips by hand and private links must stay private.
- Desk "Today's calls" is derived from ride_requests plus ride_events (late_called, no_show, confirmed_by_call, call_no_answer, place_confirmed); waitlist calls log to ride_waitlist_calls via ride_waitlist_calls_due(). Why: every coordinator call is auditable without new ride state.
- Ride tables grant nothing to anon unless an anon RLS policy exists (only rights_questions SELECT today); authenticated never gets TRUNCATE, REFERENCES or TRIGGER, and append-only ride_events, ride_admin_log and ride_waitlist_calls get no UPDATE or DELETE. Default privileges for postgres in public no longer grant tables to anon, so every new table must GRANT explicitly. Why: RLS must not be the only wall between the public and rider data.
- Autocab outbound dispatch runs only through coordinator-authorized autocab-book with service-only quote/operation claims; autocab_live defaults false (held TEST), settings are admin-only, and bounded autocab-poll caches are desk-only without rider-stage changes. Ambiguous create failures keep the claim and are never automatically retried. Why: manual texting stays available without duplicate cars or private rider-link disclosure.
- Autocab resolved request bodies stay in service-only short-lived quotes, are cleared after success or definitive rejection, and never enter ride_events; expired unused quotes are removed on the next quote request. Why: address resolution must not create permanent duplicate rider records.
- Autocab LIVE requires the selected customer's accountCode, captured only by the admin test action into ride_settings verification fields within 10 minutes, to equal the expected account code; validate_autocab_settings enforces it and blocks client edits of verification fields. Why: the key can open the wrong zTrip system.
